> 버전은 GitHub Releases의 최신 정식 릴리스를 표시합니다. CI 상태는 `main`의 마지막 워크플로 실행을 기준으로 합니다.
사람과 AI 에이전트가 함께 쓰는 팀 파일 저장소입니다. 팀원은 웹에서 파일을 올리고 정리하고, AI 에이전트는 MCP를 통해 같은 접근 권한 안에서 파일을 찾고 읽습니다. 먼저 구글 드라이브의 기본 파일 관리 기능을 대체하고, 이후에는 파일명을 몰라도 질문만으로 관련 문서와 출처를 찾는 기능을 추가합니다.

## 개요

팀이 파일을 보관하고, 사람은 웹에서, AI 에이전트는 MCP에서 **같은 저장소의 파일을 권한에 맞게 찾고 열 수 있도록** 하는 서비스입니다. Studio API와 별도 저장소에서 개발합니다.

기존 PostgreSQL과 1코어·1GB 앱 서버를 사용하는 경우 [OCI 배포 및 설치 가이드](deploy/README.md)를 참고합니다.

## 로컬에서 시작하기

필수: Node.js 24, npm, Python 3.10 이상(본문 추출용). PostgreSQL과 S3 호환 저장소 연결을 확인하려면 Docker Compose가 필요합니다.

```sh
npm ci
python3 -m venv apps/api/extraction/.venv
apps/api/extraction/.venv/bin/pip install -r apps/api/extraction/requirements.txt
npm run dev
```

- 웹 GUI: <http://127.0.0.1:3000>
- API 상태: <http://127.0.0.1:4000/healthz>
- 사용자 인증 MCP: 로그인 후 **MCP 연결**에서 발급한 Bearer 토큰으로 `/api/mcp`에 연결합니다. [클라이언트 설정](#사용자-인증-mcp-연결)을 참고하세요.
- 로컬 부트스트랩 상태 도구만 시험할 때: `CIBO_ENABLE_LOCAL_MCP=true npm run dev` 후 클라이언트를 <http://127.0.0.1:4000/mcp>에 Streamable HTTP로 연결합니다. 개발용 상태 도구 1개뿐이며, 기본적으로 꺼져 있고 운영 모드에서는 사용할 수 없습니다.

```sh
cp .env.example .env
docker compose up -d --wait
npm run infra:check
npm run typecheck && npm test && npm run build
```

### 팀 문서 공간 실행
위 Docker 서비스를 시작한 뒤 루트 `.env`에 다음 값을 설정하고 `npm run dev`를 실행합니다. API는 시작할 때 PostgreSQL 스키마와 기본 문서 공간을 초기화합니다. Docker 계정과 포트는 로컬 개발용입니다.

- `GOOGLE_CLIENT_ID`에는 Google 웹 애플리케이션 OAuth 클라이언트 ID를 입력합니다. 해당 클라이언트의 승인된 JavaScript 원본에 웹 주소를 등록하고, `CIBO_WEB_ORIGIN`도 같은 값으로 설정합니다. 기본값은 `http://127.0.0.1:3000`입니다.
- `CIBO_MASTER_GOOGLE_SUB`에는 최초 관리자의 검증된 Google 계정 식별자(`sub`)를 입력합니다. 식별자를 모르면 이 값을 비운 채 지정할 계정으로 먼저 로그인합니다. 운영자는 DB에서 승인 대기 계정의 `oidc_issuer`가 `https://accounts.google.com`이고 검증된 이메일이 대상 계정과 일치하는지 확인한 뒤 `oidc_subject`를 설정합니다. API를 재시작하고 같은 계정으로 다시 로그인하면 기존 계정이 활성 관리자가 됩니다. 공간 접근은 관리 화면에서 별도로 부여합니다.
- 팀원이 처음 로그인하면 관리자는 **계정 관리**에서 해당 계정을 활성화하고 편집 또는 조회 역할과 공간 접근을 저장합니다. 팀원은 새로고침 후 폴더를 엽니다.
- 편집자는 폴더를 생성하고 PDF·DOCX·TXT·MD·EPUB 원본을 파일당 30 MiB까지 업로드할 수 있습니다. 파일명이나 카드를 누르면 PDF는 브라우저 뷰어로, Markdown은 서식 있는 본문으로, TXT·DOCX는 텍스트로 열립니다. EPUB은 웹 리더의 목차와 이전·다음 버튼으로 챕터 본문을 읽습니다. 원본 레이아웃과 삽화는 다운로드한 책에서 확인할 수 있습니다. 원본은 미리보기 창의 다운로드 버튼으로 받습니다.
- 미리보기 API는 매 요청에서 권한을 확인하고 서버의 비공개 임시 파일에서 바이트 범위를 전송합니다. 최초 열람 때 원본 전체를 캐시에 채우며, API 프로세스당 최대 4개(합계 120 MiB), 마지막 전송 종료 후 최대 5분간 보관합니다.
- **전체 공간 검색**은 모든 활성 폴더의 파일명을 검색하고 결과에 상위 경로를 표시합니다. 폴더명 아래와 이동 대상 목록에 하위 폴더까지 포함한 파일 수를 표시합니다. 휴지통 항목은 제외합니다. 상단 **최상위로**, **한 단계 위로**, 경로의 폴더명을 눌러 이동합니다. 목록이나 격자에서 항목을 폴더 또는 상위 경로로 끌어 놓고 두 위치를 확인한 뒤 **이동 확인**을 누르면 위치가 바뀝니다. 이미 올린 파일은 이름 옆 **이동** 버튼으로 대상 폴더를 선택한 뒤 이동할 수 있습니다. 터치 화면이나 키보드에서는 **⋯ → 이동**도 사용할 수 있습니다. 편집자는 항목의 **⋯** 메뉴에서 이름 변경·이동·휴지통 이동을 수행합니다. 파일 확장자는 유지됩니다. 휴지통에서는 원래 위치로 복원하며, 같은 이름이 있으면 복원할 이름을 바꿀 수 있습니다. 상위 폴더도 휴지통에 있으면 먼저 복원합니다.
- `npm run test:drive`는 테스트 전용 PostgreSQL 스키마와 임시 S3 객체로 승인·권한·원본 저장을 검사합니다. 로그인 검증기는 테스트 대역을 사용합니다. 실제 Google 로그인은 등록한 웹 원본에서 확인합니다.

### 문서 본문과 출처

미리보기의 **본문·출처**에서 PDF는 실제 페이지, DOCX는 표 안과 빈 문단을 포함한 본문 문단 번호, TXT·MD는 원본 줄 번호를 확인합니다. PDF의 페이지 번호를 누르면 원본의 해당 페이지로 이동합니다. EPUB은 책에 지정된 읽기 순서로 본문을 추출합니다. MCP의 `get_file_metadata`는 챕터 목차와 시작 오프셋을, `read_file_text`는 챕터 번호·제목·책 내부 경로(있는 경우 앵커 포함)를 본문과 함께 반환합니다. 이미지·DRM 보호 본문은 해독하거나 OCR하지 않습니다.

파일 카드의 PDF 첫 페이지·EPUB 표지·DOCX 내장 축소 이미지는 백그라운드에서 최대 300px, 64 KiB JPEG로 만들어 PostgreSQL에 보관합니다. 썸네일 조회에도 원본의 공간·휴지통 권한을 적용합니다. 이미지가 없으면 본문 앞부분 또는 형식 아이콘을 표시합니다.

로컬 추출기는 Python 3.10 이상을 사용합니다. 위 가상환경 설치 명령을 실행하거나 `CIBO_EXTRACT_PYTHON`에 준비된 인터프리터 경로를 지정하세요. 배포용 API 이미지에는 추출기가 포함됩니다. API는 DB에 등록된 기존 파일과 신규 업로드를 백그라운드에서 한 번에 하나씩 처리합니다. 본문이 없거나 추출이 실패해도 원본 다운로드는 가능합니다. 편집자는 실패 사유를 확인하고 다시 시도할 수 있습니다.

`GET /api/files/:id/text?offset=0`은 파일명, 상태, 추출 구간(최대 10개), 다음 오프셋을 반환합니다. 각 구간에는 `unit`, 1부터 시작하는 `start`·`end`, `text`가 있습니다. 휴지통 및 현재 공간 권한 검사는 원본과 동일합니다. 추출기는 본문 200만 자·최대 8,192구간·실행 30초를 넘는 파일을 실패로 기록합니다. 텍스트는 외부 서비스에 전송하지 않고 원격 DB의 파일 ID에 연결합니다.

## 1차 목표: 팀 파일 저장소와 MCP 연결

기존 Google Drive의 **팀 파일 보관·정리·조회** 용도를 대체합니다. 웹에서 파일을 올리면 별도 동기화 없이 MCP로 같은 파일을 조회할 수 있어야 합니다. 임베딩이나 LLM 없이도 이 흐름이 동작해야 합니다.

1. **Google 로그인:** 첫 로그인은 가입 신청입니다. 사전에 지정한 마스터 관리자가 승인하고 역할과 문서 공간 접근권한을 부여합니다.
2. **웹에서 파일 관리:** 팀 폴더를 만들고 파일을 올립니다. 파일명 검색, 목록, 원본 다운로드, 이름 변경, 이동, 휴지통 및 복원을 지원합니다.
3. **MCP에서 파일 조회:** 승인된 사용자가 MCP 클라이언트 한 종류를 연결합니다. 에이전트는 해당 사용자의 폴더를 탐색하고 파일을 찾은 뒤, 지원하는 문서의 본문을 읽습니다. 원본은 권한 검사를 거치는 링크로 열 수 있습니다.

| 구분 | 1차 범위 |
| --- | --- |
| 운영 단위 | 한 팀, 한 문서 공간, 중첩 폴더, MCP 클라이언트 1종 |
| 계정 | Google 가입·로그인, 승인 대기·활성·정지, 마스터 관리자 초기 지정 |
| 권한 | 관리자·편집·조회 역할. 문서 공간 접근권한은 역할과 별도로 부여 |
| 파일 | 허용 확장자와 용량 제한 내에서 원본 보관. PDF·DOCX·TXT·MD를 우선 지원 |
| 웹 | 폴더 관리, 업로드·다운로드, 파일명 검색, 이름 변경·이동, 휴지통·복원 |
| MCP | 읽기 전용 폴더 탐색, 파일 검색, 메타데이터·텍스트 조회 |
| 제외 | Google Docs/Sheets 공동 편집, 외부 공개 공유, 데스크톱 동기화, Google Drive 자동 이관, 문서별 개별 공유, OCR 및 의미 검색 |

Google 로그인은 계속 사용하되 **파일 저장에 Google Drive는 사용하지 않습니다.** 기존 Drive 데이터의 실제 이관과 전환은 별도 작업으로 다룹니다. Google 문서·시트 등이 필요하면 이관 시 내보낼 형식을 따로 정합니다.

## 서비스 구조

```text
웹 UI / 관리자 화면 ─→ 파일 API ─→ 메타데이터 DB + 비공개 원본 저장소
                          ↑
AI 에이전트 ─→ MCP 서버 ──┘
```

- DB는 사용자, 공간, 폴더, 파일 ID 및 경로, 저장 객체 키, 권한과 변경 이력을 관리합니다. 폴더나 파일이 이동해도 파일 ID는 유지합니다.
- 웹과 MCP는 같은 파일 API와 권한 정책을 사용합니다. 업로드 완료 및 검증 후 목록에 표시합니다. PDF·DOCX 텍스트 추출은 비동기로 처리할 수 있으며 추출 실패가 원본 보관과 다운로드를 막지는 않습니다.
- MVP에서는 관리자 승인 및 파일 변경을 웹에서만 수행합니다. MCP에서 업로드·수정·삭제를 지원하지 않습니다.
- 원본과 메타데이터를 함께 백업하고 복원까지 검증합니다. 웹은 Next.js/React, API·MCP는 Node.js/Express와 공식 MCP SDK로 구성합니다. 메타데이터는 PostgreSQL, 파일은 S3 호환 비공개 저장소를 사용합니다.

## 사용자 인증 MCP 연결

Google로 웹에 로그인한 뒤 사이드바 **MCP 연결**에서 연결 이름을 입력하고 읽기 전용 토큰을 발급합니다. 현재 공간에 접근 가능한 활성 사용자(조회자 포함)가 발급할 수 있습니다. 토큰은 사용자와 발급 당시 공간에 묶이며, 30일 후 만료됩니다. 원문은 발급 직후에만 복사할 수 있습니다. 연결 해제는 해당 토큰만 폐기합니다.

클라이언트에서 전송 방식을 Streamable HTTP로 선택하고, 화면에 표시된 서버 주소(로컬 예: `http://localhost:3000/api/mcp`)와 `Authorization: Bearer <발급한 토큰>` 헤더를 설정합니다. 외부 배포에서는 HTTPS 웹 주소를 사용합니다. 원본 다운로드 링크를 브라우저로 열 때는 해당 웹 계정으로 로그인해야 합니다.

**검증 클라이언트: MCP Inspector CLI 2.17.0.** 아래 예처럼 사용자 전용 설정 파일을 저장합니다(권한 600, Git 제외 경로). `<발급한 토큰>`을 실제 토큰으로 교체합니다.

```json
{"mcpServers":{"cibo":{"type":"streamable-http","url":"http://localhost:3000/api/mcp","headers":{"Authorization":"Bearer <발급한 토큰>"}}}}
```

```sh
npx --package=node@24 --package=@modelcontextprotocol/inspector@2.17.0 mcp-inspector --cli --config ~/.config/cibo/inspector.json --server cibo --method tools/list --format json
```

개별 호출은 `--method tools/call --tool-name search_files --tool-args-json '{"query":"회의록"}'`처럼 지정합니다. 폴더·검색은 기본 30개(최대 100개), 본문은 기본 3구간(최대 10구간)입니다. 다음 조회에는 응답의 `nextOffset`을 `offset`으로 전달합니다.

### Codex에서 연결 확인과 범위 요약

웹의 **MCP 연결 → Codex에 연결하기**에서 현재 서버에 맞는 등록 명령을 복사합니다. 토큰은 Codex를 실행하는 환경에 설정하고 `codex mcp get cibo-drive`로 등록을 확인합니다. Codex에서 `connection_status`를 호출하면 실제 인증 성공 여부와 읽을 수 있는 공간의 색인 현황을 확인할 수 있습니다. 서버 연결 거부는 주소·실행 상태, HTTP 401은 토큰 누락·만료, HTTP 403은 계정 상태·공간 권한을 확인합니다.

“이 책 25장 전체를 요약하고 근거를 연결해줘”처럼 요청할 수 있습니다. `get_file_metadata`로 EPUB 목차 번호와 제목을 확인하고 `read_file_text`에 `range: {"unit":"chapter","start":25,"end":25}`를 지정합니다. PDF는 `page`를 사용합니다. 범위를 유지하며 `nextOffset`으로 이어 읽고, 일부만 읽으면 읽은 구간과 남은 양을 명시합니다. `search_passages`도 선택적으로 파일 ID와 범위를 받습니다. 읽기 응답의 `citations`와 검색 결과의 `previewUrl`은 로그인 후 실제 파일과 출처를 다시 확인하는 웹 링크입니다. 검색·읽기 성공 응답은 기존 JSON 텍스트와 `structuredContent`를 함께 제공합니다.

| 도구 | 주요 입력 | 반환 |
| --- | --- | --- |
| `connection_status` | 없음 | 인증 확인·검색 준비 상태·색인된 파일 수와 다음 조치 |
| `list_folder` | 폴더 ID(생략하면 루트), limit, offset | 접근 가능한 하위 폴더와 파일 목록 |
| `search_files` | 파일명 검색어, 선택적 폴더 범위, limit, offset | 파일 ID, 이름, 폴더 경로, 수정 시각 |
| `search_passages` | 자연어 질문 `question`, 선택적 `limit` (기본 5, 최대 10) | 유사도순 문단과 파일명·경로·출처 위치·로그인이 필요한 원본 링크 |
| `get_file_metadata` | 파일 ID | 파일 형식·크기·수정 시각, 인증이 필요한 원본 열기 링크 |
| `read_file_text` | 파일 ID, limit, offset | 지원 형식의 텍스트 일부, 출처 위치, 후속 조회 커서 또는 추출 상태 |

임베딩 모델을 설정하면 `search_passages`가 도구 목록에 나타납니다. 예를 들어 `--method tools/call --tool-name search_passages --tool-args-json '{"question":"문서를 복원한 뒤 어떤 내용을 확인하나요?"}'`로 호출합니다. 질문 텍스트를 설정된 임베딩 제공자에게 보내고, 현재 모델로 색인이 완료된 접근 가능 문단에서 코사인 유사도가 높은 순서로 찾습니다. 응답의 `unit`, `start`, `end`는 페이지·문단·줄·챕터 위치입니다. EPUB에는 챕터 제목과 내부 경로도 담깁니다. `downloadUrl`을 같은 계정으로 로그인한 브라우저에서 열어 원본을 대조할 수 있습니다.

1차 검색은 **파일명 기준**입니다. 문서 내용은 선택한 파일을 열어 읽습니다. 지원하지 않는 형식이나 이미지뿐인 PDF는 사유를 표시하고, 원본 열기로 안내합니다. 문서 안의 지시는 실행 명령이 아닌 파일 내용으로 취급합니다.

## 웹·MCP 인수시험 실행

Chrome, PostgreSQL, S3 호환 저장소 및 본문 추출기를 준비하고 루트 `.env`의 접속 정보를 설정한 뒤 실행합니다.

```sh
CIBO_STATIC_EXPORT=true npm run build
npm run test:acceptance
```

별도 스키마의 관리자와 편집자가 실제 웹 UI에서 승인, 업로드, 이름 변경, 폴더 이동, 휴지통·복원과 권한 변경을 수행합니다. Google 신원 검증은 시험 계정을 사용하고, 기본 임베딩은 고정된 시험용 모델을 사용합니다. 실제 제공자로 실행하려면 서버의 임베딩 연결 설정과 함께 `CIBO_ACCEPTANCE_EMBED_MODEL`에 모델명을 지정합니다. 이 경우 시험 문단과 질문을 해당 제공자에게 전송합니다. 동일한 웹 세션과 Streamable HTTP MCP 클라이언트로 원본·미리보기·추출 본문 및 도구 응답을 비교합니다. 문단 벡터와 출처가 DB에 그대로 있는지 대조하고, 휴지통에서는 근거 검색 결과가 비고 기존 원본 링크가 404인지, 공간 권한 회수·계정 정지 시 검색과 기존 링크가 모두 403인지 검사합니다. 차단 조건 사이에는 접근을 복구해 각 조건을 독립적으로 확인합니다. 시험용 스키마와 객체는 종료 시 정리합니다.

## 인증 및 전환 기준

- Google 로그인은 신원 확인에만 사용합니다. 검증된 Google 계정 식별자(`iss`, `sub`)를 서비스 계정에 연결합니다. 로그인만으로 파일 접근권한을 얻을 수 없으며, 관리 역할만으로 문서 조회권한이 자동 부여되지 않습니다.
- MCP에는 사용자별 접근 토큰을 사용합니다. Google 로그인용 ID 토큰을 재사용하지 않고, 익명 연결과 공용 관리자 키를 허용하지 않습니다. 원본도 비공개 저장소에 두고, 열기 요청마다 서버가 권한을 확인합니다.
- [x] 승인된 사용자가 폴더를 만들고 파일을 업로드한 뒤, 웹에서 찾고 내려받을 수 있다.
- [x] 선정한 MCP 클라이언트에서 같은 사용자로 폴더 탐색 → 파일명 검색 → 본문 읽기까지 동작한다.
- [x] 이름 변경·이동 후 웹과 MCP에 같은 정보가 보인다. 휴지통 이동·권한 회수·계정 정지 후에는 이전 파일 ID나 링크로도 조회할 수 없다.
- [x] [백업·복원 및 전환 연습](deploy/recovery.md)으로 수량·체크섬·권한과 웹·MCP 조회를 검증했다. 이후 승인된 파일 묶음만 복사해 비교 검증하고, 그전까지 기존 Drive를 그대로 유지한다.

## 2차 목표: 자동 RAG 색인과 근거 검색

1차 파일 API 위에 PDF·DOCX 등의 본문 추출 → 분할 → 임베딩 → 색인을 연결합니다. 에이전트는 파일명을 몰라도 질문으로 관련 문단을 검색할 수 있고, 파일명·페이지 또는 절과 함께 근거를 받습니다. 기존 웹·MCP 권한이 색인에도 적용되며, 권한이 회수되거나 삭제된 원본은 색인이 남아 있어도 노출되지 않아야 합니다.

### 검색 문단 생성과 재처리

API는 신규 문서의 추출 결과와 검색 문단을 함께 저장합니다. 기존에 추출을 마친 문서는 API 작업자가 한 파일씩 처리합니다. 같은 출처 구간 안에서 최대 800 유니코드 문자로 나누며, 긴 본문은 문단·줄·단어 경계를 우선합니다. PDF 페이지, DOCX 문단, TXT·MD 줄 범위, EPUB 챕터 번호·제목·내부 경로를 유지합니다. 파일 ID와 구간 순번, 구간 내 문자 오프셋으로 추출 본문에서 해당 위치를 다시 찾을 수 있습니다.

운영자는 마이그레이션된 DB에서 `npm run passages:rebuild -- <파일 UUID>`로 한 파일의 검색 문단을 다시 생성할 수 있습니다. 명령은 `DATABASE_URL`의 추출 완료 파일을 대상으로 현재 문단 목록 전체를 한 트랜잭션에서 교체합니다.

웹 상단의 **질문 검색**에서 질문을 입력하고 **검색**을 누르면 접근 가능한 문서에서 관련 문단을 최대 5개까지 보여줍니다. 결과를 누르면 PDF는 해당 페이지, EPUB은 해당 챕터와 본문 구간이 열립니다. DOCX·TXT·MD는 해당 추출 구간의 본문과 출처를 표시합니다.

### 문단 임베딩과 자동 색인

1GB VM에서는 API가 최대 8개 문단씩 외부 모델 서버에 보내고 벡터는 기존 PostgreSQL에 저장합니다. 서버 환경에 다음 값을 설정한 뒤 API를 재시작하면 기존 문서와 새 업로드를 자동 처리합니다. 모델명을 비워 두면 색인 작업자는 시작하지 않습니다.

```dotenv
CIBO_EMBED_MODEL=text-embedding-3-small
CIBO_EMBED_URL=https://api.openai.com/v1/embeddings
CIBO_EMBED_DIMENSIONS=1536
CIBO_EMBED_API_KEY=
```

`CIBO_EMBED_API_KEY`에는 사용할 조직의 서버 전용 프로젝트 키를 설정합니다. 사설 KURE 서버도 OpenAI 호환 `/v1/embeddings` 주소, 서버가 반환하는 모델명, 출력 차원(1024)으로 설정할 수 있습니다. 이때 키는 서버 인증 설정을 따릅니다. 차원은 응답을 검증하는 값입니다. 모든 API 인스턴스는 동일한 모델 설정을 사용하고, 자체 호스팅 모델의 가중치를 변경할 때는 버전을 구분하는 모델명으로 배포합니다.

`npm run embeddings -- failed`로 실패한 파일 ID와 원인을 확인하고 `npm run embeddings -- retry <파일 UUID>`로 해당 파일만 재시도합니다. 완료된 배치부터 이어서 처리합니다. 문단이 바뀌면 이전 벡터를 비우고 처음부터 생성합니다. 파일 전체가 완료돼야 `idx_stts_cd=ready`가 됩니다. 검색에서는 현재 모델 식별자, 완료 상태, 최신 파일 권한을 함께 검사해야 합니다.
